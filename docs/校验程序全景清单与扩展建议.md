## 1. 结论摘要

当前项目的“校验”不是一个单独脚本，而是分布在请求接入、能力裁决、生成前预检、源 DSL
检查、标准 A2UI 产物检查、编辑来源检查、模板编译和 JSX 浏览器检查等多个层次。

| 校验域 | 当前状态 | 主要入口 | 数量或规模 | 是否影响生产结果 |
| --- | --- | --- | --- | --- |
| WebSocket/Pydantic 请求校验 | 已启用 | `api/routes.py`、`api/schemas.py` | 多个请求模型 | 是，非法请求在模型调用前失败 |
| 能力与协议注册表校验 | 已启用 | `CapabilityRegistry`、`A2UIProtocolRegistry` | 2 组注册表加载器 | 是，配置缺失、版本区间冲突会失败 |
| 生成前候选计划校验 | 已启用 | `GenerationPreflight.run()` | 1 条集中预检流水线 | 是，阻断问题不会进入模型生成 |
| 标准 A2UI artifact 校验 | 默认启用 | `ArtifactValidator` → `card_validation.validate_card()` | 11 个已注册校验器，另有 1 个解析器 | 标准入口默认观测不阻断；Design Compact/Terse 入口阻断 |
| 标准 A2UI 诊断码 | 已启用 | `card_validation/` | 源码可发出 47 个唯一诊断码 | 取决于入口阻断策略和严重级别 |
| Design Compact 转换前校验 | 已启用 | `card_validation.validate_compact_dsl()` | 1 个聚合校验器 | 是，转换前错误阻断并进入修复链路 |
| 对比度校验 | 已启用 | `ContrastValidator` | 1 个质量校验器 | 纯色低于硬阈值可报 error；渐变/融球多为复核 warning |
| 扩展美学校验 | 已实现、未接生产 | `card_validation/quality/` | 11 个校验器、23 个诊断码 | 否，当前只在定向测试中直接调用 |
| 模板内部校验 | 条件启用 | `template_generation/engine/` | 多组契约、编译和转换守卫 | `enable_card_template=true` 时影响模板候选 |
| JSX 静态与浏览器校验 | 条件启用 | `multi_step_generation/` | Node 侧 54 个命名 finding code，Python 侧另有 1 个聚合码 | `enable_jsx_generation=true` 时影响 JSX 候选 |
| Skill 本地 CLI 校验 | 开发/离线使用 | 各 Skill 的 `scripts/validate_card.py` | 多套镜像及专用校验器 | 不被微服务生产运行时调用 |
| 旧 Compact DSL 校验实现 | 兼容/测试代码 | `services/compact_dsl_protocol.py` | 1 套大型旧实现 | 当前生成主链未引用其 `validate_compact_dsl()` |

需要特别注意以下事实：

1. `enable_artifact_validation` 默认是 `true`，但“启用校验”不等于“所有入口都阻断”。
2. 标准 `generateWidgetCard` 的 artifact 校验失败默认只记录并允许保存；
   `generateWidgetCardCompactDsl` 与 `generateWidgetCardTerseDslNested2` 将校验失败视为阻断失败。
3. `quality/` 下 11 个扩展质量校验器虽然已有代码和定向测试，当前生产 `pipeline.py` 中仍全部注释，
   不能对外宣称已经形成生产拦截能力。
4. 规则 JSON 中“声明了某个约束”不代表生产代码一定已经消费该字段；本文件第 13 节列出了主要缺口。

## 2. 状态口径

为避免把“有代码”误写成“线上生效”，本文使用以下状态：

| 状态 | 含义 |
| --- | --- |
| 已启用 | 当前默认配置和调用链会执行；仍需结合入口的阻断策略判断是否阻止产物保存 |
| 条件启用 | 只有对应功能或灰度开关打开后才进入该链路 |
| 已实现、未接生产 | 校验类和测试存在，但未注册到生产 pipeline |
| 开发/离线使用 | 供 Skill、CLI、本地样例或 CI 使用，不属于微服务在线运行时 |
| 兼容/测试代码 | 仓库仍保留，可能有大量测试，但当前生产调用图没有引用其校验入口 |
| 建议新增 | 本文基于工程经验提出，尚不是现行协议或已承诺需求 |

## 3. 端到端校验链路

```text
WebSocket 原始请求
  -> 传输包络与 Pydantic 类型校验
  -> App/ROM 版本与注册表选择校验
  -> 能力概述阶段：安装包与能力可用性裁决
  -> create/edit 请求归一化
  -> GenerationPreflight
       - 数据能力、参数 Schema、写入路径、展示字段
       - 事件能力、动作模板、参数 Schema、数据依赖
       - 素材 ID
       - 通过后才构造 CardSpec / TaskSpec
  -> 源 DSL 路线
       - 标准 A2UI：直接进入单位后处理
       - Design Compact：转换前严格校验 -> A2UI 转换
       - 模板：模板契约/编译/Tersel 校验 -> A2UI 或 Compact
       - JSX：静态 AST/契约/浏览器渲染校验 -> A2UI 转换
  -> 完整 WidgetArtifact 构造
  -> ArtifactValidator
       - 解析 -> hard -> semantic -> quality
  -> 根据入口策略决定：修复重试、记录后继续或阻断失败
  -> ArtifactStore 序列化与上传

edit 还会额外经过：
  来源下载边界 -> Markdown 代码块完整性 -> schemaVersion -> Pydantic artifact
  -> 编辑归一化 -> 正常生成前预检 -> 新产物残留路径检查
```

生成前的权限门禁属于主 Agent 与端工具契约，不在本仓库的 `ArtifactValidator` 内。它负责判定本轮数据
权限是否允许继续；微服务的校验器不能伪造或替代权限结果。

## 4. 生产标准 A2UI 校验入口与执行策略

### 4.1 对外与服务内入口

| 入口 | 文件 | 输入 | 输出/行为 |
| --- | --- | --- | --- |
| `validate_card()` | `card_validation/api.py` | DSL、CardSpec、artifact、有效能力、选项 | 返回结构化 `Reporter` |
| `validate_dsl()` | `card_validation/api.py` | DSL 与可选有效能力 | 过滤 CardSpec 专属诊断，返回面向模型的字符串 |
| `ArtifactValidator.validate()` | `services/validator.py` | 已构造的 `WidgetArtifact` 与协议 profile | 返回 error 字符串列表，并保存结构化修复上下文 |
| 兼容适配 `validate_card()` | `services/card_validator.py` | DSL、CardSpec、可选素材集合 | 返回 `CardValidationReport(errors, warnings)` |

`ArtifactValidator` 直接调用服务内 Python API，不执行 Skill 脚本、不启动校验子进程。运行时静态规则来自
`cloud/data/validator_rules/`，动态数据、事件、素材边界来自本次 artifact 的有效能力和其记录的能力目录。

### 4.2 阶段选择

`card_validation/pipeline.py` 定义三个阶段：

| `stage` 参数 | 实际执行阶段 |
| --- | --- |
| `hard` | 仅 hard |
| `semantic` | hard + semantic |
| `quality` | hard + semantic + quality |
| `all` | hard + semantic + quality |

默认 `stage="all"`、`max_errors=50`、`stop_on_stage_error=false`。因此默认情况下，一个 hard 诊断不会自动
阻止后续 semantic/quality 校验；只有 DSL JSON 解析失败码 `DSL_JSON_PARSE_FAILED` 会在 API 层阻止整个
pipeline 启动。若显式打开 `stop_on_stage_error`，hard 有 error 时不进入 semantic，前两阶段已有 error 时
不进入 quality。

### 4.3 不同生成入口的阻断差异

| 生成入口 | 源处理器 | `validation_failure_blocking` | 校验失败后的默认行为 |
| --- | --- | --- | --- |
| `generateWidgetCard` | Standard A2UI | `false` | 记录错误；校验重试关闭时仍可保存最后产物 |
| `generateWidgetCardCompactDsl` | Design Compact | `true` | 修复耗尽后返回 `VALIDATION_FAILED`，不保存 artifact |
| `generateWidgetCardTerseDslNested2` | Design Compact | `true` | 修复耗尽后返回 `VALIDATION_FAILED`，不保存 artifact |

默认配置：

- `enable_artifact_validation: true`；
- `enable_validation_failure_retry: false`；
- `validation_failure_max_repair_attempts: 1`。

## 5. 标准 A2UI 已启用程序逐项清单

默认 `all` 阶段共有 11 个已注册校验器；`SourceParser` 是它们之前的独立解析门禁。

### 5.1 `SourceParser`：输入解析与索引构建

文件：`widget_service/cloud/services/card_validation/source_parser.py`

主要职责：

- 从 `genui` fenced block 或原始文本取得 DSL；
- 要求非空 DSL 归一化后恰好三行，每行必须是 JSON object；
- 解析单个 CardSpec JSON object；
- 建立三类消息、组件 ID 索引、重复 ID、root、初始 DataModel；
- 收集组件树中的表达式位置和模板循环上下文，供后续校验复用。

诊断码：`DSL_JSONL_LINE_COUNT`、`DSL_JSON_PARSE_FAILED`、`CARD_JSON_PARSE_FAILED`。

边界：它负责“能否读懂输入”，不负责判断组件、能力或视觉语义是否合法。

### 5.2 `ProtocolValidator`：三行协议硬校验

文件：`protocol_validator.py`；阶段：`hard`。

主要检查：

- 每行 `version`；
- `createSurface -> updateComponents -> updateDataModel` 的固定顺序；
- 每行只能携带一个 payload，payload 必须是 object；
- 三类消息的必填字段和非空字段；
- Form `catalogId`；
- 三行 `surfaceId` 一致；
- `updateDataModel.path` 是结构 JSON Pointer，不能是表达式；
- `createSurface.styles` 只允许外壳形状/裁切字段；
- `createSurface.width/height` 出现时给出冗余 warning。

诊断码：

`DSL_VERSION_INVALID`、`DSL_MESSAGE_ORDER`、`DSL_REQUIRED_FIELD`、
`DSL_CATALOG_ID_INVALID`、`DSL_SURFACE_ID_MISMATCH`、`EXPR_FORBIDDEN_FIELD`、
`STYLE_BACKGROUND_WRONG_PLACE`、`STYLE_SURFACE_DIMENSION_REDUNDANT`。

### 5.3 `ComponentValidator`：组件结构硬校验

文件：`component_validator.py`；阶段：`hard`。

主要检查：

- `components` 必须是数组，组件 ID 唯一，root 引用存在；
- 组件必须属于允许集合；
- 组件顶层字段白名单、全局禁用字段和组件专属禁用字段；
- `id/component/src/label/children` 等必填与非空语义；
- `styles` 若出现必须是 object；
- root 的 `styles.width/height` 若出现只能是 `matchParent`；
- 普通 `children` 只能引用已声明组件 ID；
- 模板 `children` 对象的键、必填项、变量名和结构路径；
- Form 事件 handler 数量，以及 `condition/as` 禁止字段。

诊断码：

`DSL_COMPONENT_REQUIRED_FIELD`、`DSL_COMPONENT_ID_DUPLICATED`、`DSL_ROOT_NOT_FOUND`、
`DSL_COMPONENT_UNKNOWN`、`DSL_FIELD_FORBIDDEN`、`STYLE_ROOT_DIMENSION_INVALID`、
`DSL_TEMPLATE_CHILDREN_INVALID`、`DSL_CHILD_REF_NOT_FOUND`、`EVENT_ARGUMENT_INVALID`、
`EXPR_FORBIDDEN_FIELD`。

重要限制：当前实现没有消费 `style.json` 中的组件 `styles` 逐字段白名单、枚举和图片必需样式，详见第 13 节。

### 5.4 `AestheticBaselineValidator`：最小硬美学基线

文件：`aesthetic_baseline_validator.py`；阶段：`hard`。

当前只检查：

- 静态 `Text.content` 中是否出现指定 Unicode emoji 范围；
- `Text` 或 `Button` 的显式 `styles.fontSize` 是否小于 `8vp`。

诊断码：`ASSET.EMOJI_ICON`、`TYPE.FONT_SIZE_MIN`，均为 error。

它不是完整美学验收：不检查 `Button.label` 中的 emoji，不检查动态首帧解析结果中的 emoji，也不覆盖
`minFontSize/maxFontSize` 的最小值。

### 5.5 `CardSpecValidator`：CardSpec 硬校验

文件：`cardspec_validator.py`；阶段：`hard`。

主要检查：

- 顶层必填字段、允许字段和静态字符串类型；
- 标题/说明不能是表达式、绑定或 DataModel 路径；
- 标题与说明超长给 warning；
- `suggestSize` 是否属于配置尺寸；
- `dataBindings` 出现时必须是非空数组；
- 每个 binding 的必填字段；
- `writeResultTo` 必须位于 `/data/...`；
- 多个写入路径不能相同、互为父子或覆盖。

诊断码：`CARD_REQUIRED_FIELD`、`CARD_STATIC_FIELD_INVALID`、`CARD_SUGGEST_SIZE_INVALID`、
`CARD_WRITE_RESULT_PATH_INVALID`、`CARD_WRITE_RESULT_PATH_OVERLAP`。

### 5.6 `ExpressionValidator`：表达式语法硬校验

文件：`expression_validator.py`；阶段：`hard`。

主要检查：

- 动态值必须由唯一一对完整 `{{ ... }}` 包裹；
- `${...}` 不能脱离外层表达式；
- 表达式非空，长度不超过配置上限，括号深度不超过上限；
- 表达式内字符串使用单引号；
- 禁止变量、操作符和关键字；
- 函数调用只允许配置白名单，当前为 `size()`；
- 空引用和疑似把点路径误写进 JSON Pointer 的情况；
- `id`、`component`、事件 `call/as`、模板 `children.path` 等结构字段不能使用表达式。

诊断码：`EXPR_FULL_STRING_REQUIRED`、`EXPR_PARSE_FAILED`、`EXPR_FORBIDDEN_FIELD`、
`CARD_STATIC_FIELD_INVALID`。

### 5.7 `AssetValidator`：素材来源硬校验

文件：`asset_validator.py`；阶段：`hard`。

主要检查：

- `Image.src` 和 `styles.backgroundImage`；
- 必填图片路径必须是字符串或可解析的完整表达式；
- 静态资源路径匹配禁止模式时拒绝；
- 普通模式下路径必须在静态素材 allowlist；
- 有效能力模式下静态 allowlist 校验交给 `EffectiveCapabilityValidator`；
- 表达式路径无法从首帧 DataModel 静态解析时给 warning；
- 配置的远程白名单 host 会被直接放行。

诊断码：`ASSET_REMOTE_URL_FORBIDDEN`、`ASSET_PATH_NOT_DECLARED`。

### 5.8 `BindingValidator`：绑定、事件和 Schema 语义校验

文件：`binding_validator.py`；阶段：`semantic`。

主要检查：

- 非有效能力模式下，CardSpec 能力 ID 是否注册；
- 非有效能力模式下，能力参数是否有额外字段、缺少必填字段、混入表达式/绑定；
- 写入路径是否偏离能力建议根路径；
- 模板 `children.path` 是否指向数组；
- 绝对表达式路径能否由初始 DataModel 或 `writeResultTo + outputSchema` 推导；
- 相对表达式是否只出现在模板项子树，且能由数组样例或 Schema 推导；
- 非有效能力模式下，事件 handler、call、args、intent 和 params 是否在静态事件规则中；
- 静态展开数组项的可见数据下标与点击事件参数下标是否一致。

诊断码：

`CARD_CAPABILITY_UNKNOWN`、`CARD_ARGUMENT_UNKNOWN`、`CARD_WRITE_RESULT_PATH_INVALID`、
`BINDING_TEMPLATE_PATH_NOT_ARRAY`、`BINDING_PATH_NOT_FOUND`、`EVENT_CAPABILITY_UNKNOWN`、
`EVENT_ARGUMENT_INVALID`、`EVENT_ITEM_INDEX_MISMATCH`。

有效能力模式下，能力和事件白名单由下一节的校验器处理；完整参数 JSON Schema 已在生成前
`GenerationPreflight` 中检查。

### 5.9 `DisplayUnitValidator`：动态展示单位校验

文件：`display_unit_validator.py`；阶段：`semantic`。

主要检查：

- 从最终 CardSpec binding 和有效能力 `outputSchema` 收集 `displayUnits/unitIncluded`；
- `unitIncluded=true` 时禁止在表达式或相邻 Text 再次添加相同单位；
- `unitIncluded=false` 时要求表达式或紧邻静态 Text 恰好展示一次声明单位；
- 重复单位和漏单位均为 error。

诊断码：`DISPLAY_UNIT_DUPLICATED`、`DISPLAY_UNIT_MISSING`。

三个生成入口在进入该校验器前还会执行确定性“重复单位删除”后处理；漏单位不会被猜测补全，而是交给
校验器报告。

### 5.10 `CrossValidator`：DSL/CardSpec 跨文件一致性

文件：`cross_validator.py`；阶段：`semantic`。

当前检查：

- CardSpec `writeResultTo` 对应根结构是否在首帧 `updateDataModel.value` 初始化；
- 静态规则中的数据能力是否有可用 `outputSchema`。

诊断码：`CROSS_DATA_PATH_UNCOVERED`，当前为 warning。

### 5.11 `EffectiveCapabilityValidator`：本次有效能力白名单

文件：`effective_capability_validator.py`；阶段：`semantic`。

只有传入非空 `effectiveCapabilities` 时运行实际检查：

- CardSpec 数据能力必须属于本次有效数据能力；
- DSL `/data` 引用必须位于有效写入根之下；
- DSL 事件 `call + args` 必须与本次有效事件动作完全一致；
- DSL 图片和背景图必须属于本次有效素材源；
- 动态素材表达式无法静态解析或素材 ID 无法解析到路径时给 warning。

诊断码：

`EFFECTIVE_DATA_CAPABILITY_NOT_ALLOWED`、`EFFECTIVE_DATA_PATH_NOT_ALLOWED`、
`EFFECTIVE_EVENT_NOT_ALLOWED`、`EFFECTIVE_ASSET_NOT_ALLOWED`、
`EFFECTIVE_ASSET_DYNAMIC_PATH`、`EFFECTIVE_ASSET_SOURCE_UNRESOLVED`。

### 5.12 `ContrastValidator`：当前唯一启用的 quality 校验器

文件：`contrast_validator.py`；阶段：`quality`。

主要检查：

- 解析 `#RRGGBB` 与 A2UI `#AARRGGBB`；
- 将半透明前景/背景逐层合成后计算相对亮度和对比度；
- 渐变按颜色 stop 与相邻 stop 中点采样；至少三个样本时允许忽略一个孤立最差样本；
- 纯色背景低于 `3:1` 为 error，`3:1` 至 `4.5:1` 为 warning；
- 渐变场景低于建议阈值进入渲染复核 warning；
- 识别融球场景后不做静态阻断，输出端侧渲染复核 warning；
- 遇到精确 ID `template_root` 时跳过该节点及其子树的对比度检查。

诊断码：`VISUAL.CONTRAST`，严重级别随场景和比值变化。

## 7. 生成前校验与能力裁决

产物校验之前还有一组更早、更重要的确定性门禁。它们可以避免把非法候选送入模型。

### 7.1 请求包络与 Pydantic 模型

主要文件：

- `widget_service/cloud/api/routes.py`；
- `widget_service/cloud/api/schemas.py`；
- `widget_service/cloud/models/generation.py`；
- `widget_service/cloud/models/capability.py`；
- `widget_service/cloud/models/artifact.py`。

主要检查：

- WebSocket 新旧包络归一化；
- 固定业务操作名、字段类型、数组最小长度和枚举；
- create 模式标题和说明必填；
- edit 模式来源 URL 必须是非空字符串，显式传入的可继承字段不能为 `null`；
- 候选事件禁止额外字段；
- TaskSpec App 版本语法；
- 数据与事件能力模型中的 JSON Schema 自洽性；
- artifact 的 `schemaVersion` 固定为 `widget-artifact-v2`。

Compact DSL WebSocket 路由还会识别工具层把整个 `arguments` 错误地字符串化、或只留下传输字段但没有展开
业务字段的情况，并在进入业务模型前拒绝。

### 7.2 `CapabilityRegistry`：能力快照和版本区间

文件：`services/capability_registry.py`。

主要检查：

- 能力目录和版本快照存在；
- App/ROM 版本区间结构和版本字符串合法；
- 区间 `minInclusive < maxExclusive`；
- 任意两个能力注册表区间不能重叠；
- 运行时只能命中唯一快照；
- 数据、事件和素材文件能解析为对应 Pydantic 模型。

### 7.3 `A2UIProtocolRegistry`：协议 profile 与 Design Compact profile

文件：`services/protocol_registry.py`。

主要检查：

- 协议 profile、引用的 Markdown 和 Design Compact prompt 文件存在；
- App/ROM 协议区间合法、互不重叠且唯一命中；
- Design Compact profile 是 object；
- wire `version`、`catalogId`、尺寸集合以及每个尺寸的宽高合法。

### 7.4 `DeviceCapabilityResolver`：能力概述阶段的设备裁决

文件：`services/device_capability_resolver.py`。

当前生产调用的是 `resolve_capability_overview()`：

- 按配置限定的包名范围查询 IDS 结果；
- 精确匹配依赖包；
- 过滤停用或依赖不满足的数据能力；
- 生成可用数据能力、不可用能力、事件能力和素材概述。

同文件还保留生成阶段的数据 binding/事件裁决方法，但当前 `WidgetGenerationService` 生成主链使用的是
`GenerationPreflight`，不要把两套实现同时描述为正在串行执行。

### 7.5 `GenerationPreflight`：模型调用前的集中预检

文件：`services/generation_preflight.py`。

这是生成阶段真正的候选计划校验中心，通过后才构造 CardSpec 和 TaskSpec。

数据候选检查：

- 能力 ID 是否注册或已停用；
- `arguments` 是否通过 Draft 2020-12 JSON Schema；
- 静态能力参数中是否混入表达式或 PathBinding；
- `writeResultTo` 是否为 `/data` 下的严格 JSON Pointer；
- 候选展示字段是否是 `outputSchema` 中可解析的叶子；
- 多个写入路径是否相同、互为父子或覆盖。

事件候选检查：

- 事件 ID 是否注册；
- `action.call` 是否与注册表模板一致；
- `action.args` 是否通过参数 JSON Schema；
- 动态参数必须是完整表达式；
- 实际数据引用是否只来自注册动作模板允许的位置；
- 模板要求的数据引用不能丢失；
- 引用路径是否能由有效数据 binding 的 `writeResultTo + outputSchema` 支撑；
- 缺少支撑数据的可选事件会被移除并产生 warning，非法路径会阻断。

素材候选检查：素材 ID 必须在当前能力注册表中存在。

主要预检 issue code 包括：

`UNKNOWN_CAPABILITY`、`DATA_ARGUMENT_SCHEMA_INVALID`、`DATA_ARGUMENT_BINDING_FORBIDDEN`、
`WRITE_RESULT_PATH_INVALID`、`OUTPUT_FIELD_PATH_INVALID`、`WRITE_RESULT_CONFLICT`、
`EVENT_CALL_MISMATCH`、`EVENT_ARGUMENT_SCHEMA_INVALID`、`EVENT_EXPRESSION_INVALID`、
`EVENT_DATA_PATH_INVALID`、`EVENT_DATA_REFERENCE_MISSING`、`EVENT_DATA_DEPENDENCY_REMOVED`、
`NO_EFFECTIVE_CAPABILITY`。

预检 issue 还携带字段路径、期望值、实际类型、是否可重试、Agent 动作、修复指令和规则来源，适合直接用于
确定性修复或模型修复，而不是只返回一段不可定位的错误文本。

### 7.6 edit 来源 artifact 校验

文件：`services/source_artifact_repository.py`、`services/edit_request_normalizer.py`。

主要检查：

- mock/remote 下载模式、文件存在、超时和最大字节数；
- UTF-8 解码；
- genui 和 Design Compact 源文本长度上限；
- Markdown fenced blocks 不得重复；
- `schema` block 必须存在、是合法 JSON，且 `schemaVersion` 为 `widget-artifact-v2`；
- 必需的 `cardspec/genui/taskspec/effectivecapabilities/removedcapabilities/generationplan/meta` 块齐全；
- 各块组合后必须通过 `WidgetArtifact` Pydantic 模型；
- 来源失败不能静默降为首次生成；
- edit 归一化按“省略继承、显式数组替换、空数组清空”处理。

生成服务还会检查已移除的数据写入根是否仍残留在新 DSL 中。新 URL 与来源 URL 不同、来源不可覆盖等约束
由生成服务和存储流程共同保证，并不全部位于 `ArtifactValidator` 类中。

## 8. Design Compact DSL 转换前校验

### 8.1 当前生产入口

文件：`card_validation/compact_dsl_validator.py`；入口：`validate_compact_dsl()`。

它在 Design Compact 转成标准 A2UI 之前执行，错误抛出 `CompactDslValidationError`，warning 通过
`CompactDslValidationResult` 返回。

检查内容：

1. 解析：每行 tuple 能否由 `parse_compact_dsl_rows()` 解析为组件行或数据行。
2. 容器：`Row/Column/List/Stack` 不能是空 children，不能用空容器充当 spacer。
3. `ActionUnit`：只允许 `capsule` 与 `icon-round`；children、label、icon、onClick 组合必须合法。
4. 事件：onClick 必须恰好一个 handler，只含 `call/args`，并与 TaskSpec 事件候选完全匹配。
5. 表达式：完整占据字符串、唯一 wrapper、至少一个 `${/json/pointer}` 引用，引用必须是绝对 JSON Pointer。
6. PathBinding：必须是唯一 `path` 字段且指向绝对 JSON Pointer。
7. 首帧数据：每个绑定路径必须有 Compact DSL 数据行。
8. TaskSpec 边界：`dataModelSchema` 必须是 object，数据路径必须已声明，数据行类型必须匹配 Schema。
9. 高度预算：对 `Column/List` 汇总固定高度、margin、padding、gap 和 `ActionUnit` 的确定展开高度；只有可证明
   的最小占用超过可用高度时才阻断。
10. 使用率：CardSpec 声明的数据根没有被任何组件使用时给 warning。

它当前使用错误文本而不是稳定的细粒度诊断码。进入统一生成流水线后，错误整体映射为
`COMPACT_DSL_VALIDATION_FAILED`，warning 映射为 `COMPACT_DSL_VALIDATION_WARNING`。

### 8.2 转换器不变量守卫

文件：`services/compact_dsl_a2ui_converter.py`。

转换器除格式修复和 Design Token 展开外，还保留最终守卫，例如：

- 行结构、组件头、children 和 root 顺序；
- 重复组件、丢失引用和不合法组件值；
- `ActionUnit` 的状态、label/icon/onClick；
- 不支持或遗留 Design Token；
- 根组件外壳与背景归一化；
- 组件类型和动态绑定转换。

这些守卫属于“不能安全转换就失败”，不替代转换前的 TaskSpec-aware 校验，也不替代转换后的标准
`ArtifactValidator`。

### 8.3 旧 `compact_dsl_protocol.py`

`services/compact_dsl_protocol.py` 同时包含大型预修复、绑定、布局、语义和旧版 `validate_compact_dsl()`。
当前云侧生产代码没有导入这个校验入口；它仍被 `tests/test_compact_dsl_protocol.py` 大量测试覆盖，属于
兼容/测试实现。后续应明确“保留兼容、迁移能力或删除”的生命周期，避免维护者误以为两套 Compact
validator 会同时生效。

## 10. 模板链路的内部校验

默认 `enable_card_template=false`。打开后，模板路线会在标准 artifact 校验之前增加多层内部守卫。

### 10.1 配置和注册表校验

主要文件：

- `template_generation/controls.py`：控制文件 schema、禁用 provider/template ID 去重；
- `engine/cardplan/registry.py`：manifest 元数据、模板控制项、分发资源一致性；
- `engine/cardplan/provider_bundle.py`：provider manifest、兼容性、能力、数据 Schema、模板版本号和文件边界；
- `engine/cardplan/theme_bundle.py`：主题基础定义和主题模型；
- `engine/cardplan/template_retrieval.py`：检索 query 中的能力字段、JSON Pointer 和动作 ID。

### 10.2 Provider Template 语法与契约

`provider_bundle.py` 还负责：

- 模板体只能有一个合法组件；
- 组件、参数、children slot、插值、条件守卫和 `EventAction` 的语法；
- children 下标唯一、连续且不越界；
- 动态 binding、字符串插值和 Expr 引用已声明参数；
- 事件只能位于批准的 onClick 位置；
- 资源路径相对且不能逃逸 bundle，文件类型、UTF-8、大小和禁止键合法；
- provider 能力 ID 唯一，数据 Schema 路径及版本与目录一致。

### 10.3 CardPlan/UX 编译期校验

`engine/cardplan/compiler.py` 负责大量确定性合同检查，主要分为：

- 卡片外壳参数和可信字面量；
- 允许的 Template、UX Layout、UX Action 和业务组件集合；
- 模板参数、参数关系、状态、variant、role 和素材语义；
- 动作 ID 与 TaskSpec 事件候选的一致性；
- layout/action slot、业务组件摆放和尺寸适配；
- 原始组件预算、展开后组件预算和树深预算；
- 必需数字、必需业务组件、必需模板组和动态 binding；
- 编译后不允许泄漏 Template、UX Layout、UX Action 或高级业务组件到最终 A2UI。

### 10.4 Tersel 与表达式校验

`engine/tersel_converter.py` 和 `engine/a2ui_expression.py` 负责：

- 输入非空和总大小；
- 只允许受控 AST 语法和直接 Catalog 调用；
- root 类型、组件白名单、组件数不超过 256、嵌套不超过 32；
- 字符串、数组、对象和 literal 深度/数量上限；
- 禁止危险对象键、重复键和 keyword argument；
- `$theme(...)` 必须引用批准主题；
- `Expr(...)` 的语法、路径和函数边界；
- 数据路径必须位于 TaskSpec 声明范围；
- 内部字段不得泄漏；
- 组件 props、必填值、children 和 Design Token 可转换。

### 10.5 模板输出适配

`template_generation/source_adapter.py` 检查模板 A2UI：

- 恰好三条协议消息且 JSON 合法；
- 三条消息类型与 `v0.9`；
- `surfaceId` 一致；
- components、root 和 root styles 存在；
- 再按目标处理器转为标准 A2UI 或 Design Compact。

最终产物仍应经过统一 `ArtifactValidator`，模板内部校验不能取代标准协议、绑定、能力、素材和单位校验。

资源请求和运行时异常。聚合码用于提示修复模型重构父级布局，而不是继续逐个移动子组件。

### 11.3 JSX 转换后协议校验

`jsx_to_a2ui/validation/protocol_validator.py` 在编译输出上再次检查：

- A2UI 消息类型、版本、surfaceId、catalogId 和 updateDataModel；
- 标准组件集合、唯一 ID、单一 root 和 children 引用；
- props/styles 白名单；
- 颜色格式、枚举和数值范围；
- PathBinding/Expression 与禁止 FunctionCall 位置；
- Image、Progress、Button 等组件必填及数值关系。

之后最终标准 artifact 仍进入统一 `ArtifactValidator`。

## 12. Skill 与本地开发校验器

### 12.1 在线 Skill CLI

入口：`skills/harmony-card-generation-online/scripts/validate_card.py`。

它支持 DSL、CardSpec、artifact、有效能力、能力目录、阶段、输出格式、最大错误数、严格模式和阶段短路。
默认输出面向模型的报告；只有显式 `--fail-on-error` 才根据诊断设置失败退出码。

微服务运行时不执行该脚本。`cloud/data/validator_rules/` 和 `cloud/services/card_validation/` 是部署快照；
同步后必须重新执行微服务侧 CodeCheck 和回归测试，不能直接把 Skill 覆盖结果当成最终代码。

### 12.2 离线生成 Skill

入口：`skills/harmony-card-generation-offline/scripts/validate_card.py`。

除通用协议/绑定/能力校验外，还可显式 `--enable-aesthetic` 启用离线 `QualityValidator`。它是离线直出、
修复和历史视觉评审工具，不是在线微服务协议依据。

### 12.3 独立模板 Skill

主要入口：

- `skills/harmony-card-template-generation/scripts/validate_card.py`；
- `skills/harmony-card-template-generation/scripts/validate_templates.py`。

专用校验包括 `TemplateConstraintValidator`、模板 manifest schema/shape、固定骨架契约、模板 ID、区域、组件
变体以及逐模板生成产物检查。

### 12.4 设计生成 Skill

主要入口：

- `skills/harmony-card-design-generation/scripts/validate_card.py`；
- `skills/harmony-card-design-generation/scripts/validate_templates.py`。

专用校验包括 `DesignPlanConstraintValidator`、设计计划 schema、分层设计系统目录、参考 fixture 和生成卡片

### 12.5 独立 DSL 校验目录

`harmony-card-dsl-validation/` 也维护一套通用协议、能力、素材、颜色和美学 validator。它应被视为独立开发
工具或迁移来源，不应与在线微服务的部署快照混称为同一个运行时实例。

## 13. 当前实现与方案之间的主要缺口

以下内容是本次代码阅读发现的“现状差距”，不是已经批准的方案变更。

### 13.1 组件 styles 白名单未在标准校验器落地

`style.json` 已声明 `commonStyleFields`、`componentStyleFields` 和 `enumValues`，但当前生产
`ComponentValidator` 只检查组件顶层字段，没有逐项验证 `component.styles` 的字段名、枚举、数值类型和范围。

影响：协议外样式（例如未正式确认的 `backdropBlur`）可能绕过标准 validator。

建议：新增独立 `StyleValidator`，或在 `ComponentValidator` 中只保留结构、将样式校验集中到专用类；先依据
方案确认正式样式白名单，避免误杀模板/融球现有产物。

### 13.2 root shell “必须完整”尚未完整执行

方案要求 root 包含 `width/height/padding/borderRadius/clip/background`。当前标准代码只在 width/height
已出现且不是 `matchParent` 时报错；字段缺失不报错，padding、borderRadius、clip 和背景也没有形成统一
hard 校验。

建议：增加 `RootShellValidator`，对完整性、类型、固定值和唯一背景来源给出稳定诊断码，并为普通、融球、
模板三种场景分别建立正反例。

### 13.3 图片布局必填样式只存在于配置

`style.json.imageRequiredStyles` 声明 `width/height/objectFit`，但标准生产 pipeline 没有对应硬校验。

建议：纳入 `StyleValidator` 或新增 `ImageContractValidator`，同时验证明确尺寸、objectFit 枚举、素材来源和
动态路径初始值。

### 13.4 标准 A2UI 的通用布局闭合校验不足

当前确定性高度预算只在 Design Compact 转换前执行；休眠的 `Layout2x4Validator（已移除）` 只覆盖 `2x4` 的部分
Row/Column 闭合。标准 A2UI `2x2` 与一般 `2x4` 没有统一 hard 布局预算。

建议：提取共享的布局 IR 和二维预算器，覆盖主轴、交叉轴、padding、margin、gap、固定尺寸、百分比、
`layoutWeight/flexShrink` 和模板循环的不确定性；对“无法静态证明”与“可证明溢出”使用不同严重级别。

### 13.5 规则配置中存在潜在圆角不一致

2026-09-08 按用户确认恢复固定根圆角规则及 `layout.json.rootBorderRadius`（默认 18）。
`protocol.json.sizes.2x4.borderRadius` 当前为 22，但现行 CardSpec 校验只消费尺寸 key，
因此仍属于潜在配置漂移；本次恢复不修改协议尺寸配置，后续需另行确认是否统一。

### 13.6 扩展美学规则全部休眠

字号阶梯、间距阶梯、颜色格式、渐变、文案、密度、槽位和 `2x4` 布局等 11 个校验器当前不在生产
pipeline。现有 `AestheticBaselineValidator` 只覆盖 emoji 和小于 8vp 的显式字号。

建议：先以 shadow/report-only 模式收集历史产物命中率和误报样本，再逐码启用；不要一次性把 21 个 error
规则全部设为阻断。

### 13.7 场景标记仍有可信度风险

`ContrastValidator` 只根据 root 直接子节点 ID 判断融球，并按精确 ID `template_root` 跳过模板子树。
如果组件 ID 可由模型或外部输入控制，单独的 ID 不是可信来源证明。

建议：融球复用 `quality.common` 中的完整外壳验证；模板豁免应同时绑定可信模板生成来源、结构摘要或 artifact
元数据，不能仅凭可伪造 ID。

### 13.8 素材远程地址口径需要统一

方案正文强调拒绝网络图；当前 `asset.json` 配置了 3 个允许远程 host，`AssetValidator` 对这些 host 直接
放行。

建议：由方案负责人确认“端侧资源路径”和“云侧映射后的受控 OBS/CDN URL”是否属于同一例外契约，再统一
方案、配置、校验器和测试。确认前不要简单删除 allowlist，也不要继续扩大 host 范围。

### 13.9 `validate_card(artifact=dict)` 不等于完整 artifact schema 校验

直接 API 会从 dict 中抽取 genui、CardSpec 和有效能力，但不会逐项验证 artifact 的 schemaVersion、所有
具名块、generationPlan 和 meta。生产 `ArtifactValidator` 的入参已经是 `WidgetArtifact`，edit 来源也会先经
`SourceArtifactRepository` + Pydantic，因此生产构造路径有上游保障；独立 API 调用者容易误解其覆盖范围。

建议：新增显式 `validate_artifact_document()`，区分“对象模型校验”“Markdown 块校验”“DSL/CardSpec
语义校验”，并在命名和文档中明确三者差异。

### 13.10 诊断注册不完整集中

47 个现役诊断码中只有 11 个在中文诊断 JSON 中登记，其余消息内联；Compact、模板和 JSX 又使用不同的
code/文本模型。

建议：建立统一诊断注册表，至少包含 code、owner、阶段、默认严重级别、阻断资格、消息模板、修复提示、
文档链接和首次引入版本；CI 校验“代码发出的码必须已登记”。

### 13.11 新旧 Compact DSL validator 生命周期不清晰

新的 TaskSpec-aware 校验器已进入生产，旧 `compact_dsl_protocol.validate_compact_dsl()` 仍有大量测试。
两者规则重叠但输出模型不同，容易形成修复器与生产判定不一致。

建议：做一次规则对照表和差异测试，决定哪些旧规则迁入新入口、哪些仅属于旧协议，最后给旧入口增加明确
deprecated 标记或移除计划。

### 13.12 知识索引引用了当前不存在的美学 fixture

`agents.d/development-loop.md` 描述了 `test_aesthetic_rule_fixtures.py`、生成器、两套 fixture 目录和 503 个
测试的成功信号，但这些路径在当前工作区均不存在。当前实际存在的是 `tests/test_quality_validators.py` 等
定向测试。

建议：确认这些 fixture 是尚未合入、被误删还是来自另一分支；确认后再修正文档或补齐资产。未确认前不应
把“503 个测试通过”写进交付结论。

## 14. 建议扩展的校验维度

以下是基于生成式 UI、配置驱动协议和云端产物交付经验提出的扩展方向。它们应先进入方案评审，再进入
配置、实现和测试。

### 14.1 P0：优先补齐确定性协议闭环

| 建议 | 目标 | 推荐落点 | 最低测试 |
| --- | --- | --- | --- |
| `StyleValidator` | styles 字段、类型、枚举、数值范围、动态值允许位置 | 标准 `card_validation` hard 阶段 | 每个组件一组合法/非法字段与枚举 |
| `RootShellValidator` | root shell 完整、固定圆角/clip、背景位置、matchParent | hard 阶段 | 普通、融球、模板、缺字段、错字段 |
| `ImageContractValidator` | width/height/objectFit、源、初始值、比例 | hard + semantic | 静态、表达式、远程、未声明、缺样式 |
| `ArtifactDocumentValidator` | schemaVersion、具名块唯一/齐全、模型字段、大小 | artifact 载入边界 | 缺块、重复块、错版本、超限、非法 UTF-8 |
| 共享布局预算器 | 标准/Compact/模板使用同一几何规则 | 独立布局模块 | `2x2/2x4` 主轴、交叉轴、嵌套、未知高度 |
| 规则自检 | protocol/style/layout/asset 配置内部一致 | 服务启动或 CI | 圆角、尺寸、组件、诊断码、Schema 引用漂移 |

### 14.2 P1：安全与可信边界

| 维度 | 建议检查 |
| --- | --- |
| 外部内容不可信 | 外部工具文本不能改变能力 ID、写入路径、事件 call、权限结论或协议字段；结构化结果必须过既有 Schema |
| 来源 artifact | 保持大小、超时、不跟随重定向等边界；若要增加 URL 来源限制，必须先改方案并明确由网关、网络策略还是业务层负责 |
| 素材安全 | MIME/扩展名一致、SVG 禁止脚本/外部引用、解压炸弹和超大尺寸、受控 CDN 签名/时效策略 |
| 表达式安全 | 除语法白名单外增加 token 数、运算成本、字符串结果上限和病态表达式测试 |
| JSON/树资源预算 | 组件总数、树深、children 数、对象字段数、字符串总量、DataModel 首帧大小和 artifact 总大小 |
| 隐私 | 标题、说明、静态文案、日志和样例值不得落真实敏感数据；敏感 Schema 字段强制使用脱敏 sampleValue |
| 配置供应链 | 能力、协议、素材和诊断配置增加版本、摘要、原子发布、回滚与启动时完整性校验 |

### 14.3 P1：运行时一致性

云侧静态校验只能证明“产物在生成时自洽”，还需要端侧或联调校验：

- 端侧能力返回值严格符合对应 `outputSchema`，或经过可审计的归一化；
- `writeResultTo` 写入正确 surface，不能跨卡片或越界覆盖；
- 刷新计划频率、后台资源和失败退避合法；
- 动态数据为空、权限变化、能力卸载、超时、部分字段缺失时有明确 UI 状态；
- 运行时值带/不带单位与云侧元数据一致；
- 更新后绑定组件确实重渲染，不需要重新请求云侧生成；
- 事件动态参数在真实数据下仍满足类型和目标约束。

### 14.4 P1：无障碍、国际化和内容安全

| 维度 | 建议检查 |
| --- | --- |
| 无障碍 | 可点击元素有可理解标签；纯图标动作必须有 accessibility；阅读顺序与视觉顺序一致；最小触控区；不能只靠颜色表达状态 |
| 动态字体 | `minFontSize/maxFontSize` 成对、范围合法，关键文本不因缩放丢失；对大字号系统设置做渲染回归 |
| 国际化 | 中英文、数字、日期、RTL、CJK/Latin 混排、长地名和长日程标题；字符数限制逐步升级为测量宽度或语言感知规则 |
| 文案真实性 | 静态标题/按钮不得宣称有效需求或有效能力之外的功能；被移除能力不能以静态文字残留 |
| 隐私展示 | 锁屏、桌面和通知可见场景的敏感内容分级；必要时要求模糊、摘要或用户明确选择 |

### 14.5 P2：视觉与交互质量

在 11 个现有休眠质量校验器基础上，可继续扩展：

- 主焦点识别与视觉层级：不能只用 ID 关键词，应结合字号、面积、位置和对比度；
- 点击热区冲突：嵌套 onClick、重叠热区、过小热区、动作语义重复；
- 颜色角色：背景、正文、次级文案、状态色和品牌色之间的 token 关系；
- 复杂背景对比度：按文本真实矩形采样，而不是只按祖先颜色集合；
- 图片裁切：objectFit 与主体安全区、透明素材在不同主题下的可见性；
- 空白质量：区分必要留白和无意义空洞，不只按单一阈值；
- 信息密度：按可见语义项、动态值、动作和层级综合计算，不只统计组件数；
- 设计一致性：同卡圆角、字号、字重、间距和图标风格使用受控 token 家族；
- 动效/状态：若后续协议支持，校验 loading/error/empty/permission-denied 的一致表达。

### 14.6 P2：测试技术与质量治理

建议补充：

1. 属性测试：随机生成 JSON Pointer、表达式、组件树和写入路径，验证不会崩溃且保持诊断确定性。
2. 模糊测试：JSONL、Markdown fenced blocks、Tersel AST、Compact tuple 和 SVG 输入。
3. 变异测试：人为删除校验条件，确认测试确实会失败，避免只有正例覆盖。
4. 差分测试：在线 Skill 快照、微服务 validator、Compact 转换后 validator 对同一 artifact 给出可解释差异。
5. Golden corpus：保存真实通过、真实误报和真实漏报，按版本回放。
6. 兼容矩阵：App/ROM/profile/能力快照/尺寸/生成入口组合回归。
7. 诊断契约测试：code、severity、jsonPointer、修复提示在非破坏性版本内稳定。
8. 失败注入：模型超时、validator 异常、OBS 失败、来源 artifact 下载失败、配置缺失和 Schema 损坏。
9. 性能测试：大组件树、深表达式、大 DataModel、并发校验的 P50/P95/P99 和内存峰值。
10. 误报率治理：每个质量码记录命中量、采纳修复率、人工确认误报率和按入口/模板/场景分布。

## 15. 建议的启用与阻断路线

对新增或休眠校验器，推荐按以下顺序推进：

```text
规则和诊断码评审
  -> 正反例与历史样本离线回放
  -> shadow：只记录，不进模型修复，不影响响应
  -> report-only：返回 warning，观察误报和修复可行性
  -> repair-enabled：允许一次修复，但仍不阻断标准入口
  -> 小流量 blocking：仅确定性 hard 规则
  -> 全量 blocking：达到误报率、稳定性和时延门槛后
```

建议按规则码启用，不按整个校验器一次性启用。例如 `COLOR.INVALID_FORMAT` 可能适合较早阻断，而
`DENSITY.SINGLE_PRIMARY_ACTION` 更适合长期保持 warning。

上线门槛至少应包含：

- 规则有唯一 owner 和权威来源；
- 正例、边界例、反例、历史回放全部通过；
- 有稳定诊断码和可执行修复提示；
- 校验器异常不会导致不可控服务崩溃；
- P95 校验时延和内存开销达标；
- 误报率和规则命中分布已评估；
- 标准、Compact、模板、JSX 入口行为差异有文档和测试；
- 回滚只需关闭单码或单组规则，不需回滚整个服务。

## 19. 维护检查清单

- [ ] 是否先确认 `docs/云侧方案设计.md`，且没有用历史模板替代正式协议。
- [ ] 是否明确校验发生在生成前、转换前、artifact 阶段还是端侧运行时。
