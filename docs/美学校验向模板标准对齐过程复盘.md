# 美学校验向模板标准对齐：方案演进与实施过程复盘

> 2026-09-10 更新：密度校验已取消显式操作数量上限和单一主要操作提示；下文相关旧规则仅作历史记录。当前仅保留大字号数字数量检查，以云侧方案设计为准。

日期：2026-09-10

范围：模板生成设计值与云侧美学校验规则的对齐

## 一、这次工作的核心判断

本次工作的起点是：项目已经有正式模板、主题和转换器，但美学校验中的部分数值表与判定假设并非从这些生成源建立。完整启用校验后，模板可以稳定生成的设计，也可能被校验器判为不合规。

用户明确指定“模板里的值为标准”后，修正方向随之确定：先确认正式模板实际表达了什么，再让校验器准确接受这些设计，同时保留对标准以外输入的检查能力。

实施结果是：107 个模板预览直接执行完整质量校验器，诊断数从 404 条降到零；正式主题、模板变体、越界反例和公开入口等相关回归最终共 1221 项通过。这个结果说明本次覆盖范围内的生成与静态校验已经一致，不等同于完成端侧渲染或可访问性验收。

本文重点记录问题如何被发现、设计依据如何确定、方案如何收敛，以及验证如何证明修改有效。正式约束以[云侧方案设计](云侧方案设计.md)为准，具体数值、配置路径和维护命令见[模板美学白名单对齐记录](../widget_service/cloud/services/card_validation/模板美学白名单对齐记录.md)。

## 二、对齐前：校验能力已经接入，设计依据仍存在分离

### 2.1 本次对齐之前完成了什么

此前已完成两项相关工作：

1. 明确公共质量分流：公共根同时直接引用模板与融球背景时跳过质量阶段；只有融球背景时仅运行融球专项；其余场景运行完整质量管线。
2. 将 `quality/` 目录下全部 11 个声明级校验器接入完整分支，加上融球专项、Stack 文字分区和通用对比度，共 14 项。

这解决了校验是否执行、哪些场景执行哪些校验的问题。当时相关回归 1075 项通过，证明接入和既有测试可以正常运行。

但“既有测试通过”还不能证明正式模板与这些规则一致。若测试基线和校验器都沿用同一组旧假设，它们可以彼此一致，却共同遗漏正式模板中的合法设计。

### 2.2 差异来自两种依据并存

生成侧的依据分布在业务模板、布局模板、操作模板、主题配置和转换器中；校验侧则有独立的字号表、间距表、按钮圆角要求、密度预算和布局计算方式。

例如，模板中可以使用固定比例字号、日程局部负外边距、不同大小的操作圆角，以及带 `layoutWeight` 的自适应分区。旧校验分别假设字号属于较小的整数集合、各种间距共用一张表、按钮圆角不能过小，以及声明的 `matchParent` 可以直接按完整父宽累加。

这些假设各自有合理的初始用途，但需要与实际模板设计核对。若不先确认依据，修改很容易变成逐个消除当前报错，后续模板稍有变化又出现新的冲突。

## 三、第一步：先确定标准来源和修改边界

### 3.1 采用用户明确指定的模板标准

这次没有让校验器反向要求正式模板改字号、改颜色或改布局。用户已经明确了冲突裁决方式，因此先把“以正式模板设计值为基准”同步到方案总文档，再调整实现和测试。

基准来源分为五层：

| 来源 | 用来回答的问题 |
| --- | --- |
| `resources/source/providers/*/templates/*.cardtpl` | 业务内容、布局和操作模板实际声明了哪些样式与组织方式？ |
| `resources/source/themes/*/theme.json` | 正式主题如何组合前景色、背景、渐变、表面和圆角？ |
| `resources/source/themes/base/theme-base.json` | 统一安全边距、间距和不同尺寸的密度预算是什么？ |
| `engine/tersel_converter.py` | 模型使用通用设计名称时，最终会展开成什么字号、按钮尺寸和圆角？ |
| `engine/cardplan/preview_dataset.py` | 上述定义经过实例化和转换，实际产生什么标准组件树？ |

这里的“模板标准”是可以定位到正式生成源的设计，不是任意历史样例中的所有值，也不是一次模型输出中的偶然取值。

### 3.2 提前固定不会随本次对齐扩大的范围

本次修改集中在美学配置和相关判定语义。模板源文件、组件生成逻辑、端侧协议、能力边界和三类质量分流保持原有职责。

颜色格式、渐变结构等规则如果已经兼容正式模板，就通过验证确认兼容，不为了体现“对齐”而改动。对比度设计例外也需要具体配色依据，不能由一个组件名字获得整卡放行资格。

## 四、第二步：建立可复现的差异基线

### 4.1 同时读取声明值和实际产物

先对模板、主题和转换器中的设计值进行梳理，再调用已有预览构建入口生成当前 107 个业务模板预览。这样可以同时看到“源模板声明的值”和“转换后校验器实际读到的值”。

只搜索源码中的数字不足以判断语义。例如同一个 `12` 可能是字号、圆角、外边距，也可能是根安全边距；主题引用在模板里是符号，转换后才会成为具体颜色；`matchParent` 是否占满父级，还取决于该子项是否参与加权布局。

### 4.2 对齐审计直接执行全部质量校验器

审计没有通过公共管线的场景分流判断“模板通过”。每个预览解析成校验上下文后，直接执行完整质量校验器，统计诊断码、出现次数、模板来源、组件位置、实际值和期望值。

这样可以把两个问题分开：

- 生产运行时，这个场景应当执行哪些检查？
- 如果逐项检查正式模板，其设计是否被规则正确理解？

前者由公共质量分流回答；本次对齐主要解决后者。两个问题混在一起，会把“检查被跳过”误当成“规则与模板已经一致”。

### 4.3 第一轮审计得到的证据

| 诊断类别 | 条数 | 代表性发现 |
| --- | ---: | --- |
| 文字对比度 | 240 | 模板固定前景与底色组合触发现有通用阈值 |
| 字号 | 97 | 缺少正式字号档位；单独声明 `minFontSize` 被拒绝 |
| 间距 | 52 | 日程与耳机等模板使用未登记的局部间距 |
| 横版布局闭合 | 15 | 加权子项的父宽被重复累加 |
| **合计** | **404** | **发生在 107 个模板预览上** |

404 是诊断条数，不是失败模板数；同一个模板可以产生多条诊断。该基线也没有证明其它类别永远没有问题，只说明这些类别是当前预览样本中实际暴露的差异。圆角和操作密度等还需要结合通用转换器、布局模板和主题基础规范继续检查。

## 五、第三步：先给差异分类，再决定怎么修改

审计后没有把所有问题都归成“白名单缺值”，而是按原因分为四类。

| 差异类型 | 判断依据 | 修正方式 |
| --- | --- | --- |
| 数值覆盖不足 | 正式模板使用了确定且合法的数值 | 补齐有来源的配置档位 |
| 字段或布局语义不一致 | 同一个声明被生成侧和校验侧解释成不同含义 | 修正判定逻辑和关联预算 |
| 正式设计与通用评价阈值不同 | 模板固定配色受认可，但通用对比度规则仍会报告 | 登记精确的设计例外，保留通用检查 |
| 已经兼容 | 来源和实际产物均未暴露差异 | 保留规则，增加兼容性验证 |

这个分类决定了后面的实现边界：字号增加新档位，间距拆分适用位置，弹性布局修复计算方式，对比度引入精确组合，其余已一致的约束继续保留。

## 六、第四步：逐类推导并落实修改

### 6.1 字体：补档位，也纠正自适应范围的解释

正式模板除常见整数档位外，还使用 `9.14`、`13.71` 这样的固定比例字号，以及 `24`、`28`、`30`、`34`、`38`、`56` 等显示字号。因为这些值来自正式模板，本次将它们加入字号表，并保留原有合法档位。

另一类字号诊断与数值本身无关。模板可能写：

```json
{"fontSize": 24, "minFontSize": 12}
```

旧校验要求 `minFontSize` 与 `maxFontSize` 成对出现，因此即使两个数值都合法，也会报错。对照模板语义后，修改为：没有显式最大字号时，以 `fontSize` 作为上界；显式上下界仍需有序。

验证因此分成两部分：合法档位和单独下界应通过；未登记字号、下界大于上界、无法确认有效范围等仍应被检出。只扩充字号表无法解决第二类问题。

### 6.2 间距：从共用档位转为按属性登记

模板中的日程微调使用 `margin.top = -2`，其它局部区域还使用旧表之外的间距值。若只把这些数值加入一张通用表，`-2` 就可能同时被用于 padding 或组件间距，扩大了模板从未认可的范围。

因此保留根安全边距 12vp，并把局部规则拆为 padding、margin、组件间距三张表。负值 `-2` 只进入 margin 表；组件间距和 padding 继续拒绝负值。

对应反例直接检验扩展边界：合法的日程外边距可以通过，但负 padding、负组件间距和未登记负外边距不能通过。模板值的适用位置也是标准的一部分。

### 6.3 圆角：识别不同尺寸控件属于同一设计体系

模板体系包含 14/16vp 的通用按钮圆角、15vp 的图标操作圆角和 18vp 的胶囊操作圆角。旧的最低圆角和单一档位假设，会把部分标准控件误判为不一致。

本次将按钮最低圆角调整为 14，并接受登记的 14、15、16、18、20 组合。根卡片圆角仍按 18/20 检查，局部控件圆角不会反向改变根卡片要求。

这里的设计判断是：体系一致不要求所有不同尺寸的控件取同一个数值。验证要允许登记组合，同时保留过小圆角及未登记组合的反例。

### 6.4 区域组织：修正弹性预算，而不是扩大画布容差

横版误报的代表情况是：两个子项都声明 `width: "matchParent"`，同时用 `layoutWeight` 分配横向空间。旧校验把每个子项都按完整父宽计入，导致总占用远大于父宽。

明确这个原因后，修改方向是按主轴权重分配剩余空间：先扣除固定尺寸、外边距和组件间距，再给加权子项分配尺寸，并将分配结果传入其子树检查。

以回归中的简单例子说明：父宽 320、左右 padding 各 12，内部宽度为 296；固定子项宽 80，间距为 8，则加权子项可获得 208。其后代宽 208 可以成立，宽 220 应继续报告越界。

这也补上了只修正父级加总容易遗漏的环节：父级通过之后，后代必须使用分配后的宽高检查；加权子项声明的最小尺寸也不能超过可分配空间。

### 6.5 信息密度：让数量预算和动作分类有明确依据

主题基础规范给出了尺寸预算：2x2 最多两个主要操作，2x4 最多一个。本次同步显式操作上限，并把根容器的整卡隐式入口从显式操作计数中排除。

数量硬上限与多主操作提示继续分别表达：2x2 两个显式操作可以不触发数量超限，但仍保留多主操作提示；2x4 两个显式操作会触发超限。

大字号数字上限没有因本次对齐顺带提高。当前模板审计没有提供必须调整该上限的证据。

### 6.6 对比度：将被认可的设计组合与通用检查分开

对比度是此次诊断最多的一类。用户认可模板值，不代表这些固定配色都会达到通用的 3:1 或 4.5:1 阈值。因此需要明确表达“这个设计组合被允许”，而不是把所有输入的阈值一起降低。

最终采用可生成、可追溯的精确配色白名单：

1. 从 14 套正式主题和 107 个模板预览收集前景色及背景合成结果。
2. 将同一前景与完整背景样本集合组成一条记录，去重后得到 51 个组合。
3. 为组合保留主题路径或模板 ID 来源，写入独立配置。
4. 运行时只读取配置，不加载模板生成器。
5. 同时匹配前景与完整背景集合时接受该标准组合；不匹配时继续执行原对比度检查。

这种表达支持同一标准配色被不同组件复用。匹配不依赖组件 ID，也不因为颜色相近就放行；前景相同但背景不同仍需检查。对于渐变，要求整个背景样本集合匹配，不能只命中某一个色标。

新增反例使用“标准前景配非标准背景”和“非标准低对比度前景配原背景”，确认配置没有扩大成颜色级或整卡级豁免。

这里接受的是用户认可的模板设计例外。背景样本是声明值合成的静态结果，不能表述为端侧实测像素；低于通用阈值的组合也不能因此宣称达到可访问性标准。

### 6.7 颜色、渐变结构和安全边距：确认兼容后保留

正式主题使用的 ARGB 格式、透明度档位、渐变方向及色标结构已经被支持，根安全边距也已一致。因此这些方面没有扩大格式或结构白名单。

14 套主题新增了直接校验，覆盖主题文字、辅助内容、操作或辅助表面以及渐变。保留已有正确规则，同样是本次对齐的结果。

## 七、第五步：修正测试依据，避免把旧假设继续固化

### 7.1 先让正式模板成为正例

新增测试让每个模板预览直接运行完整质量校验器，并确认输入没有被校验过程修改。这验证的是校验器对产物的判断能力，而不是依靠校验器修补输入后取得通过。

随后扩展到两个预览列表之外的范围：

- 14 套主题的文字与表面组合。
- 所有正式模板变体中的固定字号、字重和间距，包含操作、布局模板。

这样可以避免只对 107 个当前预览调参，而遗漏未被该预览集实例化的正式定义。

### 7.2 旧负例为何必须迁移

调整标准后，一部分旧测试失败，因为原来选作负例的值已经变成正式合法值。例如 3vp 外边距、16vp 按钮圆角和 14vp 标题，不能继续被用来证明校验器能识别越界。

处理时先修改测试生成器，再重新生成数据：

| 原负例 | 新的验证意图 |
| --- | --- |
| 3vp 外边距 | 改用未登记的 9vp 外边距 |
| 16vp 按钮圆角 | 改用低于模板最低档位的 12vp |
| 14vp 标题 | 改用不在标题档位内、但属于合法通用字号的 24vp |
| 18 与 20 的按钮圆角组合 | 改为包含未登记 22vp 的组合 |
| 旧尺寸动作数量预算 | 2x4 两操作检查硬上限；2x2 两操作检查多主操作提示 |

这保留了“正常对照、单点修改、预期诊断”的测试结构。不能只删掉失败断言，也不能手改生成产物来迁就结果。

### 7.3 公开入口也需要回归

直接校验器通过后，再验证模板编译后的公开入口：只有模板标记的任意低对比度内容不能获得放行；双标记场景仍按既有规则跳过；去掉模板标记后的融球场景转入融球专项。

这一步确认精确配色例外没有改变场景分流，也没有恢复已取消的单模板标记豁免。

## 八、验证收敛过程与前后结果

验证是逐层扩展的，以下数字对应不同范围，不能当作同一个测试集的性能对比，也不能相加。

| 阶段 | 范围与结果 | 说明 |
| --- | --- | --- |
| 对齐前诊断基线 | 107 个模板预览，404 条诊断 | 定位真实设计差异；诊断数不是失败模板数 |
| 首次修正后模板审计 | 同一批预览，零诊断 | 直接执行完整质量校验，不经过豁免分流 |
| 初步整组回归 | 1202 项通过 | 包含模板正例、核心越界反例及既有相关回归 |
| 补充主题与模板变体检查 | 1217 项通过 | 加入 14 套主题与正式模板固定值覆盖 |
| 补充模板编译公开入口 | **1221 项通过** | 最终相关回归范围 |
| 配色配置一致性 | **通过** | 51 个组合可由正式来源重新生成 |
| 美学单点数据一致性 | **716 个文件通过** | 23 条规则、230 个负例和 230 个正常对照 |
| 静态与格式检查 | **12 个 Python 文件通过** | Ruff 静态检查及格式检查 |
| 差异空白检查 | **通过** | 工作区与暂存区分别检查 |

本地测试存在缺失配置时，沿用项目已有的进程内补齐方式；没有修改磁盘配置。上述结果来自本次实现阶段，本复盘文档的编写没有重新执行整套代码测试。

从方案角度看，前后变化可以概括为：

| 维度 | 对齐前 | 对齐后 |
| --- | --- | --- |
| 标准依据 | 生成设计与校验假设各自维护 | 正式模板设计作为本轮对齐依据，方案和记录同步 |
| 差异定位 | 单个报错容易被视为模型生成问题 | 从模板群体产物统计诊断，再回查来源和语义 |
| 数值约束 | 较粗的共用档位 | 有来源、区分属性用途的档位 |
| 布局判断 | 声明尺寸被直接累加 | 识别加权分配，并校验分配后的子树 |
| 配色接受方式 | 通用阈值覆盖全部普通配色 | 精确标准组合与通用阈值并存 |
| 验证依据 | 既有规则样例 | 正式模板正例、主题、变体、越界反例和公开入口共同验证 |

## 九、这次过程沉淀出的维护方法

### 9.1 后续模板变更应如何进入校验

当正式模板或主题发生变化时，先定位生成源，再判断是数值新增、语义变化还是配色组合变化。需要变更规则时，先同步方案，再更新配置或实现，最后运行模板覆盖与反例回归。

固定配色通过同步工具重新生成并执行一致性检查。其它数值配置目前仍需有意识地维护，模板变体覆盖测试负责发现遗漏；本次没有实现所有设计值自动反向同步到校验配置。

### 9.2 看到诊断时应先问哪几个问题

1. 这个值来自正式模板、转换器默认值，还是一次任意输入？
2. 是值没有登记，还是校验器误解了字段或布局语义？
3. 放宽后会影响哪些属性、尺寸或场景？
4. 能否保留一个只差一处的有效反例，证明检查能力仍在？
5. 通过的是实际单项检查，还是因为分流没有执行检查？

### 9.3 结果的适用边界

本次证明了当前正式来源与静态校验在已覆盖范围内的一致性。动态长文本、不同设备字体测量、完整端侧渲染，以及融球模糊后的实际可读性，仍需各自的验证环节。

尤其需要区分三个结论：模板设计被接受、静态检查通过、端侧实际显示合格。它们可以互相提供证据，但不能彼此替代。
