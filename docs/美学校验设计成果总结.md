# AI 卡片美学校验设计成果总结

## 1. 文档目的

本文从方案起点、问题暴露、规则重构、特殊背景适配、验证证据和生产启用边界六个方面，系统总结 AI 卡片云侧美学校验的设计成果。重点覆盖三个实现区域：

- `widget_service/cloud/services/card_validation/quality/`：11 个扩展美学校验器及公共能力；
- `widget_service/cloud/services/card_validation/contrast_validator.py`：文字与背景对比度校验；
- `widget_service/cloud/services/card_validation/aesthetic_baseline_validator.py`：最小审美硬基线。

本文是成果说明和维护指南，不替代正式方案。协议、硬规则、校验链路和启用口径仍以 [`云侧方案设计.md`](./云侧方案设计.md) 为准。`output/`、`health_sport.jsonl`、`meeting.jsonl` 和 `sleep.jsonl` 用于回归、结构理解与历史视觉参考，不是正式协议来源。

## 2. 一页结论

本次工作的核心成果不是把若干审美偏好机械编码，而是建立了分层、可解释、可配置、能识别场景边界的美学质量体系：

| 层级 | 主要实现 | 解决的问题 | 当前生产状态 |
|---|---|---|---|
| 最小硬基线 | `AestheticBaselineValidator` | emoji 图标和极小字号等低争议硬问题 | 已接入静态校验链路 |
| 可读性专项 | `ContrastValidator` | 纯色、透明色、渐变、模板和融球背景下的文字可读性 | 已接入 quality 阶段 |
| 扩展设计契约 | `quality/` 下 11 个校验器 | 颜色、渐变、素材、图标、形状、字体、文案、间距、区域、密度和 2x4 布局 | 代码与测试已完成，生产 pipeline 仍注释停用 |

11 个扩展校验器相对原实现完成了以下结构性升级：

1. 从硬编码规则升级为正式配置驱动；
2. 从遍历扁平组件数组升级为理解 root 可达树、父子关系和内容根；
3. 从只看静态字面值升级为解析首帧静态文本、Expression 和 PathBinding；
4. 从按 ID 猜测融球升级为验证完整、受控的融球组件树；
5. 从所有诊断默认 warning 升级为默认 error、仅两项明确 warning 的白名单策略；
6. 从普通卡片单场景规则升级为同时覆盖普通渐变和融球背景；
7. 从无系统测试升级为 47 个定向用例，并以 60 份普通样例和 3 份典型背景样例进行批量实测。

当前严重级别决策为：

| 诊断码 | 严重级别 | 原因 |
|---|---|---|
| `ICON.DUPLICATE_SRC` | warning | 图标复用可能是设计选择，需要提示但不宜直接阻断 |
| `DENSITY.SINGLE_PRIMARY_ACTION` | warning | “单一主操作”是视觉建议；尺寸硬上限由另一条规则负责阻断 |
| 11 个扩展校验器产生的其它诊断 | error | 违反正式设计契约或形成确定性布局、格式、密度风险 |

该白名单只约束 11 个扩展校验器。`ContrastValidator` 有独立的对比度分级策略，`AestheticBaselineValidator` 的两项诊断均为 hard-stage error。

## 3. 设计背景与演进过程

### 3.1 初始目标

云侧生成链路要求 A2UI 模型只生成 GenUI DSL，真实的协议裁决、校验、降级和产物保存由微服务负责。视觉质量因此不能依赖主 Agent 的口头约束，也不能只依赖模型“尽量生成得好看”，必须形成可执行校验。

早期设计采用三种逐步补齐的能力：

- 先建立最小硬基线，阻止明显不可接受的结果；
- 再加入对比度计算，解决文字可读性；
- 最后增加 11 个扩展质量校验器，将设计规范转成细粒度诊断。

### 3.2 关键演进节点

| 时间 | 演进节点 | 主要成果 |
|---|---|---|
| 2026-09-01 | 初次集成 `ContrastValidator` | 支持 ARGB、透明度合成、相对亮度和纯色/渐变候选对比度 |
| 2026-09-03 | 增加 `AestheticBaselineValidator` | 把 emoji 图标和小于 8vp 的字号纳入 hard 阶段 |
| 2026-09-04 | 增加 11 个 `quality/` 校验器 | 首次形成颜色到布局的扩展规则集合 |
| 2026-09-04 | 对比度支持模板边界和渐变采样 | 精确跳过 `template_root` 子树，增加渐变中点与候选背景处理 |
| 2026-09-07 | 统一尺寸来源 | 密度和 2x4 规则只从 CardSpec 的 `suggestSize` 获取尺寸 |
| 2026-09-07 | 对比度适配渐变与融球 | 渐变低对比进入渲染复核，融球不再被默认白底误判 |
| 2026-09-08 本轮 | 11 个扩展规则系统重构 | 修复语义、场景、配置、路径、严重级别和测试覆盖问题 |

### 3.3 原方案的主要缺陷

原方案有规则雏形，但很多实现只能处理“扁平、静态、普通背景、显式数值”的理想输入。批量样例和融球用例暴露出五类共性问题：

1. **数据语义不足**：动态 Text、PathBinding 和首帧 DataModel 无法参与标题、数字等语义判断。
2. **组件树语义不足**：部分规则遍历所有组件，部分只看 root 直接子节点，不能区分可达组件、包装容器和嵌套动作。
3. **场景语义不足**：融球背景和前景是兄弟分支；按普通父子树检查会错误要求外壳 `padding:12`，也会错误计算文字背景。
4. **配置没有真正生效**：字号、字重、间距、圆角和尺寸上限在代码中硬编码，配置文件无法成为统一规则源。
5. **诊断语义过松**：扩展校验公共入口默认 warning，导致确定性违规无法阻断；同时少数设计建议又不适合全部升级为 error。

本轮重构的目标因此不是扩大规则数量，而是让规则的输入、场景、阈值、诊断路径和严重级别都能被准确解释。

## 4. 美学校验总体架构

### 4.1 三层职责

```text
完整 artifact / GenUI
        │
        ├─ hard：AestheticBaselineValidator
        │        └─ 最小、低争议、可阻断基线
        │
        ├─ semantic：协议、组件、表达式、素材、绑定、CardSpec 等一致性
        │
        └─ quality
                 ├─ ContrastValidator（当前已启用）
                 └─ 11 个扩展校验器（当前未启用）
```

三层不是重复检查：

- hard 基线回答“这个结果是否明显不应交付”；
- semantic 回答“这个结果是否符合协议、能力和数据契约”；
- quality 回答“这个结果是否满足可读性和设计契约”。

### 4.2 pipeline 的真实启用状态

当前 `pipeline.py` 中：

- `AestheticBaselineValidator()` 位于 `STATIC_VALIDATORS`，按 hard 阶段执行；
- `ContrastValidator()` 位于 `QUALITY_VALIDATORS`，已执行；
- 11 个扩展校验器已经导入，但实例仍以注释形式保留，没有进入生产执行列表。

因此必须区分三种状态：

| 描述 | 是否成立 |
|---|---|
| 11 个校验器已有实现 | 是 |
| 11 个校验器已有定向测试和批量样例结果 | 是 |
| 11 个校验器已经生产启用 | 否 |

本轮成果属于“规则修复、配置收敛、场景适配、测试建设和启用准备”，不能表述为“11 个规则已经在线阻断”。

### 4.3 阶段选择与短路

`selected_stages()` 的行为为：

| 请求阶段 | 实际执行阶段 |
|---|---|
| `hard` | hard |
| `semantic` | hard → semantic |
| `quality` / `all` | hard → semantic → quality |

开启 `stop_on_stage_error` 时，hard 阶段已有 error 会阻止进入 semantic，进入 quality 前已有 error 也会终止后续检查。这意味着启用 11 个扩展校验器后，还需要结合调用方是否开启短路判断实际诊断可见性。

## 5. 11 个扩展校验器的公共基础重构

`quality/common.py` 是本轮变化的核心。原文件主要提供组件遍历、颜色提取和统一上报；当前已经发展为 11 个校验器共享的场景与语义基础设施。

### 5.1 颜色解析与诊断路径

原八位颜色 alpha 读取使用 `raw[6:8]`，实际读到的是蓝色通道。当前按照 DSL 的 `#AARRGGBB` 约定读取 `raw[:2]`，修复透明度判断的根本错误。

同时完成：

- 静态颜色只认可八位 `#AARRGGBB`；
- Expression、动态路径和 `$theme(...)` 不作为静态格式错误；
- 渐变颜色的指针从不完整的 `linearGradient/<index>` 修正为 `linearGradient/colors/<index>/0`；
- alpha 档位可以由 `style.allowedAlphaSteps` 配置。

### 5.2 严格融球场景识别

新增 `QualityScene`，将卡片分为 normal、template 和 fusionBall，并分别记录 shell root 与 content root。

融球场景不能只凭一个 ID 判定。当前必须同时满足：

1. 公共 root 是 `Stack`；
2. root 恰好有两个直接分支，且第一个是 `fusionBallBackground`；
3. 第二个前景根 ID 以 `__genui_render_component__` 开头；
4. 背景分支是 `Stack`；
5. 背景 children 的顺序和数量为大球 slot、中球 slot、小球 slot、玻璃层；
6. 三个 slot、三个球和玻璃层的组件类型正确；
7. slot 到球体的 children 引用完整；
8. 前景根为受控容器类型。

以上完整结构识别仍由 `quality.common` 提供，供 Slot 等调用方使用。2026-09-09 按用户确认，Spacing 改为独立定位实际前景层，不再以完整装饰树作为边距转移条件，具体见 7.8；其它调用方不随之放宽。

### 5.3 组件树能力

公共逻辑新增：

- `parents_by_id()`：建立组件到父节点集合的反向映射；
- `iter_reachable_components()`：只遍历从 root 可达的组件并防止循环；
- `contains_action()`：递归查找区域内的真实非空点击 handler；
- `children_of()`：安全解析 children 引用。

这些能力分别支撑图标同父区域去重、密度统计、动作区域排序和嵌套布局分析，避免把孤立组件或嵌套子树当成扁平列表处理。

### 5.4 首帧展示文本解析

`display_text()` 统一处理：

- 静态字符串；
- 可由首帧 DataModel 解析的完整 Expression；
- `{"path":"/..."}` PathBinding；
- 数字值。

布尔值被显式排除，避免 Python 中 `bool` 是 `int` 子类造成错误的文字或数字识别。该能力用于文案长度和大数字语义判断。

### 5.5 统一严重级别入口

11 个扩展校验器都通过 `quality.common.add()` 上报。入口使用 warning 白名单：

```text
ICON.DUPLICATE_SRC
DENSITY.SINGLE_PRIMARY_ACTION
```

其余现有或未来新增诊断默认 error。默认 error 能防止新增规则因为遗漏 severity 参数而静默退化成非阻断提示。

| 校验器 | 原方案主要问题 | 当前设计成果 | 主要严重级别 |

## 7. 11 个校验器逐项设计成果

### 7.1 ColorValidator：颜色格式和透明度

原实现只有“若能解析颜色，则检查 alpha 档位”。这带来两个漏洞：一是 alpha 读取了蓝色通道，二是不能解析的静态颜色被直接跳过。因此六位 `#RRGGBB`、拼写错误和错误渐变颜色可能不产生诊断。

当前行为：

- 所有受控颜色字段和渐变 stop 都进入统一扫描；
- 静态色必须为 `#AARRGGBB`，否则产生 `COLOR.INVALID_FORMAT`；
- 合法八位色的 alpha 必须命中配置档位，否则产生 `COLOR.ALPHA_STEP`；
- `opacity` 位于 `[0,1)` 时产生 `COLOR.OPACITY_MISUSE`，要求透明度编码进颜色 alpha；
- Expression、路径表达式和主题值不做静态格式误判；
- 配置中的布尔值不会因 Python 数值类型继承关系被当成合法 alpha。

工程价值是把“颜色能否解析”“透明度是否登记”“是否绕过 alpha 规则”拆成可定位的诊断。

### 7.2 GradientValidator：渐变结构闭合

原实现只要求渐变有 `direction` 或 `center`，未区分渐变类型；一个 stop 即可通过，也没有顺序和完整覆盖检查。

当前行为：

- 线性渐变接受最终样例使用的 `direction`，也接受 Compact 转换链路使用的 `angle`；
- `angle` 必须是 0～360 的非布尔数值；
- 径向渐变必须有非空 `center`；
- colors 至少包含两个 stops；
- 每个 stop 必须有合法八位颜色和 0～1 offset；
- offset 必须严格递增；
- 首尾 offset 必须覆盖 0 和 1；
- 非对象渐变不会继续调用 `.get()`，避免校验器异常。

这使渐变校验从“字段存在检查”升级为“可渲染结构闭合检查”。

### 7.3 AssetQualityValidator：素材来源

原实现只检查 `Image.src`，且按大小写敏感前缀判断。大写 URL、`styles.backgroundImage` 和远端白名单均未覆盖。

当前行为：

- 同时检查 `Image.src` 与 `styles.backgroundImage`；
- URL 与 data URI 判定大小写不敏感；
- 动态表达式不做静态来源误判；
- 远端 host 经过 trim、lower 归一后与规则配置比对；
- 不在白名单的 HTTP/HTTPS 和 data URI 产生 `ASSET.REMOTE_SRC`。

正式方案仍以“本地受控素材”为默认要求；host 白名单只是受控扩展机制，不表示任意网络图片可以使用。

### 7.4 IconValidator：装饰图标重复

原实现按整卡 `src` 计数，同一个业务图标在标题区和详情区各使用一次也会被认定为重复装饰。

当前行为只在“相同静态 src + 相同直接父容器集合”时提示。跨业务区或跨父容器复用不再误报，Expression 和动态路径跳过。

`ICON.DUPLICATE_SRC` 保持 warning，因为它反映的是装饰重复风险，而不是确定性协议错误。

### 7.5 ShapeValidator：根圆角与控件圆角家族

原实现仅在 root 已写圆角且值不等于 18 时报告；缺少 `styles` 或缺少 `borderRadius` 都不会报错，阈值也无法通过配置调整。

当前行为：

- 2026-09-08 按用户确认恢复 `SHAPE.CARD_ROOT_RADIUS`，root 缺少 styles 或 borderRadius 也会报告；
- root 圆角读取 `layout.rootBorderRadius`，默认只允许 18 或 20vp，不允许中间值；列表表示离散档位，兼容单个数值配置，单值提示不再重复为区间；
- Button 最小圆角读取 `layout.minButtonRadius`；
- 多个 Button 使用不一致的圆角档位时产生 `SHAPE.RADIUS_FAMILY`；
- 提示文案随配置值变化，不再硬编码 18。

### 7.6 TypographyValidator：正式字号阶梯与自适应字号

原允许集合包含 `8/24/30/38/48/56` 等历史值，并用 `int(size)` 判断，导致 12.9 被截断后可能错误通过；字重只允许 400/500/700。

当前行为：

- 字号从 `layout.allowedFontSizes` 读取，默认正式阶梯为 `10/12/14/16/18/20/32/40`；
- 使用精确数值，不截断小数；
- 字重从 `layout.allowedFontWeights` 读取，当前为 100～900、步长 100；
- 同时检查 `fontSize`、`minFontSize` 和 `maxFontSize`；
- min/max 必须成对声明，且 `minFontSize <= maxFontSize`；
- 配置中的布尔值不作为数值档位。

该规则与 hard 基线形成清晰分层：例如 9vp 不低于 8vp，因此不触发 hard 基线，但不在正式字号阶梯中，启用 Typography 后仍会触发 quality error。

### 7.7 CopyValidator：标题和动作的语义识别

原实现扫描所有组件的 `content` 和 `label`，只要是普通静态字符串就套用 8 字限制；带任意 `onClick` 的内容或 label 一律使用 4 字限制。因此普通正文容易被误认为标题，动作限制也与当前尺寸预算不一致。

当前行为：

- 只有 ID 含 `title/header/kicker` 的 Text 才按标题检查；
- Button label 和自身带非空 `onClick` 的 Text 按动作文案检查；
- 普通正文不再套用标题长度；
- 支持从首帧 DataModel 解析单字段 Expression 和 PathBinding；
- 标题默认最多 8 字，可由 `layout.titleMaxChars` 配置；
- 动作文案默认 2x2 最多 6 字、2x4 最多 8 字，可由 `layout.maxActionLabelChars` 配置。

### 7.8 SpacingValidator：间距阶梯与融球安全边距

原实现只读取数字 `styles.padding`，root 缺失 padding 时不报告，margin、itemMargin、List space 和四向对象都未检查；原允许阶梯还包含 18/20/24/32 等非正式值。

当前行为：

- 间距档位读取 `layout.allowedSpacing`，当前为 `0/2/4/6/8/10/12/14/16`；
- 检查 `styles.padding`、`styles.margin`、`itemMargin` 和 List 的 `space`；
- 支持单一数值和四向对象；
- 空对象、非法值和非登记档位都可识别；
- 2026-09-08 按用户确认恢复 `SPACING.SAFE_MARGIN`，安全边距读取 `layout.defaultPadding`，默认 12vp；
- 普通 root 缺少 styles 或 padding 时也报告该错误；
- `Stack` root 的直接子节点含 `fusionBallBackground` 且能唯一定位一个真实前景容器时，安全边距检查作用于前景；兼容带渲染前缀的内容根与 `template_root`，不要求完整球槽、球体和玻璃层；
- 普通模板的 `Stack root → Stack template_root → 带渲染前缀的真实内容容器` 检查 `template_root`，不再把外壳的 padding 0 判为内容边距错误；
- 普通 `root_0` 分支优先；仅有背景标志、缺失前景、非容器或多个前景时仍检查 root。内容 padding 缺失或不符合配置仍报错；
- 已声明的 padding 仍检查通用间距档位，不因根节点或融球场景而跳过。

安全边距规则重新区分渲染外壳与内容安全区；其它校验器的场景识别行为保持不变。

### 7.9 SlotValidator：内容区域与动作顺序

原实现只看 root 直接 children，把第一个直接子节点当标题候选，只检查直接子节点自身是否有 `onClick`。遇到 root 包装层、融球前景根、嵌套标题或动作容器时会漏报或误报。

当前行为：

- 通过 `QualityScene` 定位普通或融球的实际内容根；
- 可穿过普通的单子树包装容器，但不会把 Text 叶子错误解包成区域根；
- 递归判断一个区域是否包含动作；
- 只有最后一个主区域允许作为动作区，否则产生 `SLOT.ORDER`；
- 递归按语义 ID 查找标题；
- 标题字号读取 `layout.titleFontSizes`，当前 2x2 为 12，2x4 为 12 或 18；
- children 的诊断指针指向实际内容根，不再使用不可解析的固定 root 路径。

### 7.10 DensityValidator：动作与大数字密度

原实现遍历整个组件数组，排除 root 动作，任何非 `None` 的 `onClick` 都计数；缺少 CardSpec 时默认按 2x2 判断。大数字只依据 `fontSize >= 24`，大字号标题也会被误算，2x4 同样只允许一个大数字。

当前行为：

- 尺寸只从 `ValidationContext.cardspec.suggestSize` 获取；
- 缺少有效 CardSpec 尺寸时跳过尺寸相关结论；
- 只统计从 root 可达的组件；
- root 自身的非空动作也计入；
- 动作硬上限读取 `layout.maxExplicitActions`，当前 2x2 为 1、2x4 为 2；
- 大数字上限读取 `layout.maxLargeNumbers`，当前 2x2 为 1、2x4 为 2；
- 大数字必须是 Text、字号至少 24，且首帧展示文本以数字开头；
- 静态字符串、Expression 和 PathBinding 使用同一首帧语义。

两条动作诊断有意拆分：

| 场景 | `DENSITY.EXPLICIT_ACTIONS` | `DENSITY.SINGLE_PRIMARY_ACTION` |
|---|---|---|
| 2x2 有 2 个动作 | error，超过硬上限 1 | warning，偏离单主动作建议 |
| 2x4 有 2 个动作 | 不触发，未超过硬上限 2 | warning，提示主次关系 |
| 2x4 有 3 个动作 | error，超过硬上限 2 | warning |

### 7.11 Layout2x4Validator：递归尺寸闭合

原实现只检查带显式数值尺寸、至少两个直接子项的 Row/Column；仅支持标量 padding，不计 margin 和交叉轴；所有 Row/Column 都被强制等分。root 使用 `matchParent` 或子项尺寸未知时，规则基本失效。

当前行为：

- 仅在 CardSpec 明确为 2x4 时执行；
- 从 root 的 `matchParent` 按 320×160 profile 开始递归解析；
- 支持数值、百分比和 matchParent 等可解析尺寸；
- 计算标量或四向 padding；
- 计算子项 margin 和父容器 itemMargin；
- 同时检查主轴闭合和交叉轴溢出；
- 单子项 Row/Column 也会检查；
- 子项尺寸未知时不猜测，但已知 margin 仍计入最小占用；
- 通过 visited 防止异常组件图循环；
- 不再强制所有容器等分；
- 只有组件 ID 命中 `layout.equalSplitIdTokens` 时才执行等分契约，token 会 trim 和 lower。

这个设计把“布局一定溢出”和“布局可能未知”区分开，只对静态可证明的问题给出 error。

## 8. ContrastValidator 的完整设计成果

### 8.1 初始方案

初版 `ContrastValidator` 已具备可用的数学基础：

1. 解析六位 RGB 和八位 ARGB；
2. 将半透明前景色与背景合成；
3. 按 sRGB 线性化计算相对亮度；
4. 使用 `(Lmax + 0.05) / (Lmin + 0.05)` 计算对比度；
5. 从白色默认背景开始，沿组件树把祖先背景传递给子节点；
6. 纯色背景下 `<3:1` 为 error，`3:1～4.5:1` 为 warning。

但初版存在三类限制：

- 完整 Expression 被 `_has_text()` 排除，动态 Text 不参与校验；
- 渐变把 stop 逐个追加到背景列表并保留默认白底，可能把实际已完全覆盖的白底当作候选；
- 不理解模板内容层和融球兄弟背景。

### 8.2 当前纯色和透明色算法

当前算法仍从白色作为“无任何已知背景时”的基底，但沿祖先链逐层合成：

```text
祖先候选背景
   ↓ 与当前 backgroundColor 进行 alpha 合成
当前有效背景候选
   ↓ 继续传给 children
文字前景色与每个有效背景候选计算对比度
```

如果当前背景色完全不透明，父背景在计算结果中自然被覆盖，并清除上游渐变标记；如果背景半透明，则保留它与各个父背景候选的合成结果。

纯色场景保持严格分级：

| 对比度 | 结果 |
|---:|---|
| `>= 4.5:1` | 不产生诊断 |
| `>= 3:1` 且 `< 4.5:1` | warning |
| `< 3:1` | error |

### 8.3 渐变采样与容忍策略

当前对每个线性或径向渐变：

1. 读取所有可解析 stop 颜色；
2. 保留每个 stop 作为样本；
3. 为每对相邻 stop 增加一个颜色中点样本；
4. 将每个渐变样本与全部父背景候选合成；
5. 去除完全相同的候选颜色；
6. 对文字颜色计算全部样本比值。

渐变至少产生三个样本时，不直接使用最小值，而是排序后使用第二低值。其含义是允许一个孤立的最差边缘样本，但如果多个区域都低于阈值，第二低值仍会触发诊断。

2026-09-09 根据两份浅色渐变日程样例修正严重级别：此前即使静态比值低于 3:1 也统一产生 render-review warning，导致 ArtifactValidator 不将其纳入错误及修复上下文。当前保留第二低样本策略，但报告值低于 3:1 输出 error，3:1 至不足 4.5:1 输出渲染复核 warning，达到 4.5:1 不诊断。样例中的白色及半透明白色文字在近白背景上约为 1.02～1.03:1，必须进入错误处理。渐变仍是采样估算，真实渲染复核不能完全省略；纯色背景不应用孤立样本容忍策略。

### 8.4 动态文本统一参与

当前 `_has_text()` 将以下内容都视为需要检查的 Text：

- 非空静态字符串；
- Expression 字符串；
- 非空 PathBinding 对象；
- 其它非 `None` 值。

对比度只依赖“文字会被绘制”以及文字样式颜色，不需要知道运行时具体文案，因此动态文本不应被排除。

### 8.5 融球场景为什么不能静态硬算

融球最终结构为：

```text
root：透明 Stack
├─ fusionBallBackground：真实装饰背景
└─ __genui_render_component__root：文字内容
```

真实背景和内容是兄弟分支。仅沿内容祖先链向上查找会到达透明 root，继而错误使用默认白底，造成白色文字对白底的伪造 `1.00:1` 结果。

当前 `ContrastValidator` 在 root 直接 children 中检测到 `fusionBallBackground` 且没有 `root_0` 时，将整卡标记为融球场景。对于每个有内容的 Text：

- 不生成基于默认白底的错误比值；
- 不尝试在缺少布局坐标时静态合成三个球、玻璃层和文字矩形；
- 输出 `VISUAL.CONTRAST` warning；
- `actual` 标记 `scene: fusionBall` 和 `requiresRenderReview: true`；
- 要求端侧真实渲染后复核文字区域。

这不是“融球自动通过对比度”，而是把无法静态证明的结论从错误阻断改成显式人工/渲染复核。

### 8.6 模板内容层的精确豁免

模板生成器使用固定 ID `template_root` 标记已由模板体系控制配色的内容层。当前对比度校验：

- 仅精确匹配 `template_root`，不按前缀或大小写模糊匹配；
- 跳过该节点自身及其子树的 `VISUAL.CONTRAST`；
- 不跳过 template_root 外的并列非模板内容；
- 不影响组件、表达式、绑定、事件、素材等其它 validator。

测试覆盖了伪造前缀、不同大小写、不可达 template_root 和混合卡片，防止豁免扩散。

### 8.7 ContrastValidator 当前边界

当前实现是“结构感知的静态近似”，不是像素级渲染器，仍有以下边界：

1. 不知道文字真实 bounds、渐变方向上的空间位置和低对比区域面积；
2. 相邻 stop 使用颜色中点采样，尚未按 offset 距离和实际方向进行空间积分；
3. 融球识别主要依赖 root 直接子节点 ID，不像 `quality.common` 那样验证完整融球结构；
4. 只处理 `backgroundColor`、`linearGradient`、`radialGradient`，复杂背景图仍需要渲染侧复核；
5. 融球场景会对每个有内容的 Text 产生 warning，后续可能需要按主数字、标题、辅助文本角色聚合或分级；
6. 六位颜色仍可被对比度算法解析，这是为了兼容历史输入；正式颜色格式由 ColorValidator 负责收紧。

其中第 3 点是当前最值得优先收敛的风险：建议后续让 ContrastValidator 复用 `QualityScene` 的完整结构证明，避免伪造 ID 获得全卡 render-review 降级。

## 9. AestheticBaselineValidator 的定位与成果

### 9.1 为什么需要独立 hard 基线

完整设计契约可能随产品风格、尺寸、模板和配置变化，但有少数问题几乎不依赖视觉主题：使用 emoji 冒充图标、文字小到不可读。将它们放在 hard 阶段，可以在 11 个扩展规则尚未生产启用时仍保留最小质量门槛。

### 9.2 当前覆盖

| 规则 | 范围 | 诊断 | 严重级别 |
|---|---|---|---|
| emoji 图标 | 组件静态 `content` 中 U+1F000～U+1FAFF、U+2600～U+27BF 字符 | `ASSET.EMOJI_ICON` | error |
| 最小字号 | Text/Button 的静态数值 `fontSize < 8` | `TYPE.FONT_SIZE_MIN` | error |

数值解析支持裸数值和类似 `"7vp"` 的静态值。动态字号无法在静态阶段证明，因此当前跳过。

### 9.3 与 TypographyValidator 的分工

| 示例 | Baseline | Typography |
|---|---|---|
| `fontSize: 7` | error：低于绝对可读下限 | 同时不在正式阶梯 |
| `fontSize: 9` | 通过：不低于 8 | error：不在 `10/12/...` 正式阶梯 |
| `fontSize: 24` | 通过：满足最小可读性 | error：不在当前批准阶梯 |
| 动态 `fontSize` | 跳过 | 当前也无法静态确认具体档位 |

Baseline 保持“小而稳定”，Typography 承担“当前产品设计契约”。两者不应合并成一个不断扩张的 hard 阶段。

### 9.4 当前未覆盖项

| 未覆盖项 | 影响 |
|---|---|
| `Button.label` 中的 emoji | Button 使用 label 而不是 content，当前可能漏报 |
| 首帧 DataModel 解析后的 emoji | Expression/PathBinding 不会解析为展示文本后再检查 |
| `minFontSize/maxFontSize < 8` | Baseline 只检查 fontSize |
| emoji 范围外的符号图标 | 当前仅按两个 Unicode 范围判断 |
| 复杂字素和 variation selector 语义 | 当前逐 code point 判断，不做完整 grapheme 分析 |

这些缺口应根据“是否足够低争议、是否适合 hard 阻断”决定是否补入 Baseline；更具产品风格属性的规则应留在扩展 quality 层。

### 9.5 稳定性说明

`AestheticBaselineValidator` 自首次引入后的主体实现保持稳定。本轮没有为了扩大成果而把 11 个校验器的规则搬入 hard 阶段，这是有意维持职责边界的结果。

## 11. 普通渐变与融球场景的协同处理

### 11.1 普通渐变

普通渐变通常直接位于 root styles：

```text
root 自身 backgroundColor / linearGradient
└─ 普通内容树
```

各层职责为：

- ColorValidator 检查颜色格式和 alpha 档位；
- GradientValidator 检查方向、stop、顺序和覆盖；
- ContrastValidator 采样颜色并判断是否进入渲染复核；
- Spacing/Shape/Typography 等继续检查内容设计契约。

### 11.2 融球

融球是由标准 Stack 和 Divider 确定性展开的背景树，不是新 A2UI 组件：

```text
透明 shell root
├─ 受控融球背景树
└─ 前景内容根
```

各层职责为：

- 11 个扩展规则通过完整结构证明识别 shell/content 边界；
- Spacing 对 shell `padding:0` 合法放行，并检查前景根 12vp；
- Slot 从前景内容根开始识别标题和动作区域；
- Contrast 因兄弟背景无法沿祖先链闭合，产生 render-review warning；
- 其它颜色、字体、文案、密度和布局规则仍正常执行，不因融球整体豁免。

### 11.3 为什么两套场景识别强度目前不同

11 个扩展校验器的场景识别是本轮新建的严格结构证明；ContrastValidator 的融球识别来自较早修复，仍使用 `fusionBallBackground` 与 `root_0` 直接子节点标记。两者解决的问题不同、演进时间不同，因此当前还没有完全统一。

这项差异已经被记录为生产启用前风险，而不是被隐藏为“已完全解决”。

测试对象：`output/N001.dsl.jsonl`～`output/N060.dsl.jsonl`。

结果：60 份均可解析，11 个校验器没有抛出异常，共产生 176 个 errors、0 个 warnings。

| 诊断码 | 数量 | 发现的样例偏差 |
|---|---:|---|
| `COLOR.INVALID_FORMAT` | 73 | 60 处 `#FFFFFF` 和 13 处其它六位颜色，不符合正式八位 ARGB |
| `GRADIENT.UNREGISTERED` | 8 | 4 个文件各有 2 个六位渐变 stop；与颜色格式诊断存在交叉 |
| `TYPE.FONT_SIZE_STEP` | 15 | 使用历史字号 30vp 或 38vp |
| `COPY.TITLE_MAX_CHARS` | 20 | N001～N020 的语义标题为 9 或 10 字 |
| `SPACING.SAFE_MARGIN` | 60 | 所有样例 root 为 padding 8，正式规则为 12 |

这批结果说明两点：

1. 新校验器能够稳定处理真实生成样例，不再因为数据形态异常而崩溃；
2. 历史样例与当前正式规则存在明显代际差异，不能以“历史样例可渲染”替代当前规则合规。

本批没有同父重复图标或多主动作场景，因此两条 warning 白名单规则均未触发。

## 13. 前后方案的本质变化

### 13.1 从数值扫描到结构理解

原方案主要在组件数组上逐项看字段；当前方案开始理解：

- 哪些组件从 root 可达；
- 组件位于哪个父区域；
- 一个区域是否在深层包含动作；
- 普通 root、融球 shell 和前景内容根的职责差异；
- 首帧动态值实际会展示成什么。

### 13.2 从历史样例兼容到正式规则收敛

历史样例中的六位颜色、8vp padding、24/30/38vp 字号都可能正常渲染，但与当前正式设计契约不一致。本轮选择以 `docs/云侧方案设计.md` 和配置为规则源，把历史用例作为迁移证据，而不是反向放宽正式规则。

### 13.3 从全 warning 到风险分层

原公共上报默认 warning，无法体现格式错误、布局溢出、字号档位和安全边距等确定性问题。本轮改为默认 error，只保留图标重复和单主动作建议为 warning。

Contrast 的 warning 不属于该白名单：渐变报告值在 3:1 至不足 4.5:1 时、以及融球场景使用渲染复核 warning；普通渐变报告值低于 3:1 则为 error，不再统一降级。

### 13.4 从代码常量到规则资产

布局、字号、字重、文案长度、动作数量、数字数量、圆角、等分语义和 alpha 档位都已进入配置，并由测试证明校验器真实消费。后续调整产品规范时，不需要在多个校验器中分别改硬编码。

## 14. 当前风险与后续建议

### 14.1 生产启用前必须处理

1. **完成灰度评估**：60 份历史样例会产生 176 个 error，直接启用会显著改变现有生成链路结果；需要先明确是修生成 Prompt/转换器、迁移样例，还是分规则灰度。
2. **统一融球识别**：ContrastValidator 应复用 `QualityScene` 的完整结构证明，避免只凭 ID 获得全卡对比度降级。
3. **明确 validator 失败是否阻断**：总方案当前说明 artifact 校验默认开启但失败重试默认关闭，且失败属于非阻断观测；11 个规则内部 severity 为 error 不自动等于生成响应 failed。必须在启用方案中明确 error 的消费策略。
4. **处理重复诊断**：六位渐变 stop 会同时产生 `COLOR.INVALID_FORMAT` 和 `GRADIENT.UNREGISTERED`。内部定位合理，但用户侧展示可能需要聚合主因。
5. **确认 `backdropBlur` 协议白名单**：融球玻璃层依赖该样式，当前“未被拦截”不等于正式 profile 已明确批准。
6. **同步测试默认配置**：补齐 `default_config.yaml` 与 `config.py` 的
   `ai_widget_data_huashan_enable` 定义，否则无完整 spec 配置的本地环境会在 pytest 收集阶段失败。

### 14.2 建议的启用顺序

建议按确定性和样例影响分批启用：

1. 先启用崩溃风险低、规则高度确定的 Color、Gradient、Shape、Typography、Spacing；
2. 同步修复生成 Prompt/转换器，使新产物使用八位 ARGB、12vp 安全边距和正式字号阶梯；
3. 再启用 Asset、Density、Layout2x4，并观察素材来源、动作上限和闭合诊断；
4. 最后灰度 Copy、Slot、Icon 等更依赖语义 ID 和设计区域判断的规则；
5. 在每阶段记录命中率、重试率、最终产物成功率和误报样例，确认稳定后扩大范围。

### 14.3 后续增强方向

- 将 Contrast 与严格融球场景识别统一；
- 若端侧能提供布局 bounds 或截图，增加基于文字矩形的渐变/融球空间采样；
- 对对比度结果增加主标题、主数字、辅助文字角色分级；
- 评估 Baseline 是否需要覆盖 Button.label emoji、首帧动态 emoji 和 min/max 字号；
- 为 11 个校验器增加统一规则命中统计和按诊断码灰度开关；
- 建立“历史样例迁移前/后”双基线，避免以旧用例强迫新规则退化。

## 16. 最终评价

本轮美学校验建设已经从“若干轻量字段检查”推进为“有分层、有场景、有配置、有证据的质量体系”：

- hard 基线稳定守住明显不可交付的问题；
- Contrast 能区分可静态证明的纯色问题与必须渲染复核的渐变、融球问题；
- 11 个扩展校验器已经完成从扁平扫描到组件树与首帧语义理解的重构；
- 普通样例揭示了历史产物与正式规则的系统性差距；
- 融球样例证明安全边距等规则能够识别 shell 与 content 的真实职责；
- 严重级别已经形成默认 error、两项 warning 的可维护策略；
- 生产启用边界和未闭合风险已明确记录，没有把“测试完成”误写成“线上生效”。

从工程成熟度看，当前已经具备进入分规则灰度和生成侧同步整改的基础；下一阶段的关键不再是继续堆规则，而是把规则命中数据、生成修复策略、pipeline 消费方式和端侧渲染复核闭环真正接通。
